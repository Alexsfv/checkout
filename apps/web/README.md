# Фронтенд магазина — решение

Каталог, корзина, оформление заказа и оплата тестовой картой. Next.js (App Router) + TypeScript,
React Query для запросов, Zustand для мелкого разделяемого состояния, CSS Modules с дизайн-токенами.

## Запуск

Нужны Node.js 24.x и npm 11.x (как и для бэкенда).

```sh
npm ci                 # из корня репозитория, один раз
npm run dev:all        # API на :4000 и фронтенд на :3000 одной командой
```

Отдельно:

```sh
npm run dev:api        # только бэкенд      -> http://localhost:4000
npm run dev:web        # только фронтенд    -> http://localhost:3000
```

Сборка и запуск собранного фронтенда:

```sh
npm run build:web      # сборка @checkout/contracts + next build
npm run start:web      # http://localhost:3000, API должен быть запущен
```

Проверки:

```sh
npm run check          # форматирование, сборка и тесты бэкенда, OpenAPI
npm run typecheck:web  # tsc --noEmit
npm run test:web       # юнит-тесты фронтенда (vitest)
npm run smoke          # HTTP-проверка бэкенда, при запущенном API
```

Адрес API берётся из `NEXT_PUBLIC_API_URL` (см. `apps/web/.env.example`), по умолчанию
`http://localhost:4000`. Файл фиксации зависимостей — корневой `package-lock.json`.

## Как устроено

```text
apps/web/src/
  api/
    http/              ядро работы с сетью, ничего не знает про домен
      client.ts        сборка клиента из четырёх частей ниже
      transport.ts     отправка: fetch, таймаут, повтор потерянных запросов
      parse.ts         чтение тела, конверт {data,meta,links}, разбор ошибки
      messages.ts      перевод ошибки в понятный вид
      error-texts.ts   словари: код API -> текст, ошибка поля -> подсказка
      errors.ts        класс AppError и предикаты
      idempotency.ts   слоты ключей Idempotency-Key
      types.ts         типы транспорта, клиента и ошибок
      constants.ts     статусы для повтора, таймауты, задержки
      utils.ts         сборка URL, признак идемпотентности, пауза
    client.ts          единственный настроенный экземпляр клиента приложения
    session.ts         гостевая сессия: токен, единственное создание, сброс
    endpoints.ts       все запросы — по одной строке на запрос
    queries.ts         ключи кеша и настройки чтения
    types.ts           типы API из @checkout/contracts, своих копий нет
    constants.ts       адрес API, ключи хранилища, интервалы и сроки жизни
    utils.ts           unwrap и предикаты статусов оплаты
  ui/                  примитивы; types.ts и constants.ts — рядом
  features/            экраны: catalog, cart, checkout, order, shell
  lib/                 форма, хранилище, формат, валидация + types/constants
```

В каждой папке действует одно правило: компоненты и функции лежат в своих
файлах, а типы, константы и чистые утилиты — в соседних `types.ts`,
`constants.ts`, `utils.ts`. Магических чисел и строк в разметке нет.

### Где что менять (критерий D2)

Обязанности разнесены так, что каждую можно поменять отдельно:

| Что нужно изменить                  | Где                                          |
| ----------------------------------- | -------------------------------------------- |
| Общие заголовки, базовый адрес, 401 | `api/client.ts` — конфигурация клиента       |
| Способ отправки, таймаут, повторы   | `api/http/transport.ts`                      |
| Форма ответа и конверта             | `api/http/parse.ts`                          |
| Текст ошибки для пользователя       | `api/http/messages.ts`                       |
| Новый запрос                        | `api/endpoints.ts` — одна строка             |
| Кеш, инвалидация, опрос             | `api/queries.ts`                             |
| Что делать с ошибкой на экране      | `app/providers.tsx` + `ui/QueryBoundary.tsx` |

Компоненты не вызывают `fetch`, не собирают URL, не читают `response.status` и не разбирают
ошибки. Ошибка первой загрузки экрана показывается через `QueryBoundary` рядом с данными,
всё остальное — общей лентой уведомлений, настроенной один раз в `app/providers.tsx`.

## Принятые решения

**Гостевая сессия.** Токен подставляется провайдером заголовков лениво: первый же защищённый
запрос создаёт сессию, параллельные запросы ждут один промис. Отдельного «шлюза ожидания
сессии» перед рендером нет. `401` перехватывается один раз: токен сбрасывается, запрос
повторяется с новым (`onUnauthorized` в `api/client.ts`).

**Идемпотентность.** Ключ привязан к отпечатку тела операции (`api/http/idempotency.ts`):

- то же тело → тот же ключ → повтор вернёт уже созданный объект (`200`), а не второй заказ;
- изменившееся тело (например, новый `quoteId` после пересчёта) → новый ключ автоматически;
- явный `rotate()` — когда пользователь начинает новую попытку оплаты после отказа или отмены.

Слоты лежат в `localStorage`, поэтому перезагрузка страницы не создаёт второй заказ.

**Повтор потерянных запросов.** Транспорт сам повторяет сетевые сбои и `5xx` — но только для
безопасных методов и для `POST` с `Idempotency-Key`. Поэтому повторы React Query отключены:
дублировать их незачем.

**Расчёт доставки.** `POST /api/quotes` вызывается внутри `useQuery` с ключом
`[cartVersion, delivery]`: расчёт однозначно определяется этой парой, поэтому кешируется как
обычное чтение и не плодит лишних расчётов. Адрес курьера проходит через debounce 350 мс.
`409 CART_VERSION_CONFLICT` перечитывает корзину — вместе с версией меняется ключ, и расчёт
уходит заново без действий пользователя.

**Устаревшая корзина и расчёт.** Перед созданием заказа корзина перечитывается всегда: она
могла измениться в другой вкладке. Если итог отличается от того, что человек видит на экране,
заказ не создаётся — показываем новую сумму и просим нажать ещё раз. Списывать другую сумму
без ведома человека нельзя. Если корзина изменилась уже после расчёта и сервер ответил
`QUOTE_EXPIRED` или `CART_VERSION_CONFLICT`, расчёт делается заново по тому же правилу:
сумма прежняя — продолжаем молча, изменилась — просим подтвердить.

**Оплата.** Успех определяется статусом заказа на сервере (`paid` + `succeeded`), а не ответом
на запуск оплаты. Текущая попытка восстанавливается из `GET /orders/{id}/payments`, поэтому
перезагрузка страницы во время оплаты продолжает отслеживание. Опрос статуса живёт в
`refetchInterval` и останавливается сам на конечном статусе и при уходе со страницы.

**Устаревшие ответы.** Каждое чтение идёт со своим `AbortSignal`; React Query применяет только
последний ответ на ключ. Ответ на сохранение никогда не подменяет более свежие данные:
после мутаций данные перечитываются, а не собираются на клиенте.

**Производительность.** Никаких цепочек `map().filter()` там, где хватает одного прохода:
пересчёт корзины, индекс «товар → позиция», сборка ошибок полей и склейка классов сделаны
одним `reduce` — один обход и одна аллокация вместо трёх. Карточки каталога обёрнуты в `memo`,
чтобы изменение количества одного товара не перерисовывало весь список. Оптимистичное
обновление корзины даёт мгновенный отклик, серверный ответ остаётся источником истины.

**Форматирование.** Суммы, склонения и даты собираются вручную в `lib/format.ts`, без `Intl`.
Причина простая: это несколько строк понятного кода, поведение не зависит от набора локалей
в среде и полностью покрыто тестами (`lib/format.test.ts` — разряды, копейки, ноль,
отрицательные суммы, все ветки русского склонения).

**Описание формы.** Поля, правила проверки, набор активных полей и сборка тела запроса
разнесены по `features/checkout`: `types.ts` — форма значений, `constants.ts` — начальные
значения и наборы полей, `rules.ts` — правила проверки, `form.ts` — сборка `delivery`
и `customer`, `errors.ts` — конструкторы прикладных ошибок.

**Доступность и адаптив.** У полей есть подписи, ошибки связаны через `aria-describedby`,
первое поле с ошибкой получает фокус. Кнопка оформления намеренно не блокируется на
незаполненной форме: заблокированная кнопка не объясняет, чего не хватает, — нажатие
подсвечивает проблемные поля. Модальное окно — нативный `<dialog>`: ловушка фокуса,
Esc и возврат фокуса работают без единого слушателя. Проверены ширины 1280 и 390 пикселей,
горизонтальной прокрутки нет.

## Проверенные сценарии

Основной путь и устойчивость проверены вручную и прогоном в браузере (Playwright,
скрипты в проект не входят):

- каталог грузится из API, товар с нулевым остатком не добавляется;
- количество меняется, позиция удаляется, состав и итог совпадают с `GET /api/cart`;
- превышение остатка: сервер отклоняет запрос, корзина откатывается к прежнему состоянию;
- оба способа доставки со своими полями; смена доставки и состава корзины даёт новый расчёт,
  стоимость доставки и итог берутся из ответа сервера (в том числе бесплатная доставка
  от 5 000 ₽);
- оплата картой: успех, отказ банка, отмена, повтор после каждого из них;
- наличные: заказ сразу подтверждён (`confirmed` / `unpaid`), ни одной попытки онлайн-оплаты
  не создаётся;
- потерянный ответ на `POST /api/orders` не создаёт второй заказ;
- двойное нажатие «Оформить» и «Оплатить картой» создаёт один заказ и одну попытку;
- перезагрузка восстанавливает сессию и корзину; перезагрузка во время обработки оплаты
  доводит заказ до статуса «оплачен»;
- сбой сети не стирает форму, повтор доводит оформление до конца;
- корзина, изменённая в другой вкладке: показываем новую сумму и просим подтвердить,
  после подтверждения заказ уходит с актуальным составом и итогом;
- то же при гонке — когда корзина меняется уже во время создания заказа;
- опрос статуса прекращается после ухода со страницы;
- пустую корзину оформить нельзя;
- форма проходится с клавиатуры: Tab по полям, стрелки в радиогруппах, Enter отправляет;
- при незаполненных полях фокус уходит на первое проблемное, ошибка связана с полем
  через `aria-describedby`;
- ширина 390 пикселей: сценарий проходится целиком.

Юнит-тестами закрыта чистая логика: пересчёт корзины, правила ключей идемпотентности,
политика повторов транспорта, перевод ошибок API в текст и в ошибки полей формы
(`npm run test:web`, 27 тестов).

## Известные недоработки

- Автотестов интерфейса в репозитории нет: браузерные сценарии прогонялись отдельно, в проект
  вынесены только юнит-тесты чистой логики.
- Нет виртуализации списков — на учебном каталоге из четырёх товаров она не нужна.
- Пункт выдачи выбирается списком радиокнопок, без карты и поиска.
- Тёмная тема следует системной настройке, переключателя в интерфейсе нет.
- История заказов отдельным экраном не сделана: незавершённый заказ показывается баннером
  на каталоге и в корзине, остальное — по прямой ссылке.

## Затраченное время

Около 8 часов: слой данных и общие компоненты — примерно половина, экраны и разбор
пограничных случаев (повторы, конфликты, восстановление) — вторая половина.
