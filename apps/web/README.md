# Фронтенд магазина — решение

Каталог, корзина, оформление заказа и оплата тестовой картой. Next.js (App Router) +
TypeScript, React Query для запросов, Zustand для мелкого разделяемого состояния,
CSS Modules с дизайн-токенами.

## Запуск

Нужны Node.js 24.x и npm 11.x (как и для бэкенда).

```sh
npm ci                 # из корня репозитория, один раз
npm run dev:all        # API на :4000 и фронтенд на :3000 одной командой
```

Отдельно:

```sh
npm run dev:api        # только бэкенд      -> http://localhost:4000
npm run dev:web        # только фронтенд    -> http://localhost:3000
```

Сборка и запуск собранного фронтенда:

```sh
npm run build:web      # сборка @checkout/contracts + next build
npm run start:web      # http://localhost:3000, API должен быть запущен
```

Проверки:

```sh
npm run check          # форматирование, сборка и тесты бэкенда, OpenAPI
npm run typecheck:web  # tsc --noEmit со строгими noUnusedLocals/noUnusedParameters
npm run test:web       # юнит-тесты фронтенда (vitest)
npm run smoke          # HTTP-проверка бэкенда, при запущенном API
```

Адрес API берётся из `NEXT_PUBLIC_API_URL` (см. `apps/web/.env.example`), по умолчанию
`http://localhost:4000`. Файл фиксации зависимостей — корневой `package-lock.json`.

## Работа с API и распределение обязанностей

Все запросы идут через один клиент, собранный из четырёх независимых частей. Каждая
отвечает ровно за одно и меняется отдельно от остальных:

```text
запрос -> заголовки -> транспорт -> разбор ответа -> данные
                                 \-> разбор ошибки -> AppError -> текст для человека
```

| Обязанность                                                     | Где живёт                                    |
| --------------------------------------------------------------- | -------------------------------------------- |
| Базовый адрес, общие заголовки, гостевая сессия, повтор при 401 | `api/client.ts`                              |
| Отправка: fetch, таймаут, повтор потерянных запросов            | `api/http/transport.ts`                      |
| Чтение тела, пустые ответы, конверт `{data,meta,links}`         | `api/http/parse.ts`                          |
| Приведение любого сбоя к единому `AppError`                     | `api/http/errors.ts` + `parse.ts`            |
| Код ошибки в текст для человека, ошибки полей                   | `api/http/messages.ts` + `error-texts.ts`    |
| Ключи идемпотентности                                           | `api/http/idempotency.ts`                    |
| Сам список запросов                                             | `api/endpoints.ts`                           |
| Кеш, инвалидация, интервалы опроса                              | `api/queries.ts`                             |
| Что показать при ошибке                                         | `app/providers.tsx` + `ui/QueryBoundary.tsx` |

**Что делает общий код.** Собирает URL и заголовки, сериализует тело, ставит таймаут,
повторяет потерянные запросы, читает тело один раз, отличает пустой ответ от JSON,
разворачивает конверт, проверяет статус и превращает любой сбой — сетевой, HTTP или
разбора — в один тип `AppError` с машинным кодом и ошибками полей.

**Что делает компонент.** Получает готовые типизированные данные или уже разобранную
ошибку и решает, как это показать: подставить текст под поле, предложить повтор, показать
состояние операции. Ни один компонент не вызывает `fetch`, не читает `response.ok`, не
вызывает `response.json()` и не пишет свой `catch`. Ошибку первой загрузки показывает
`QueryBoundary` рядом с данными, всё остальное уходит в общую ленту уведомлений,
настроенную один раз в `app/providers.tsx`.

Проверка состояния операции — это другое и остаётся в коде экрана: `paymentStatus: failed`
приходит в успешном HTTP-ответе, это состояние заказа, а не разбор транспорта.

**Добавить новый запрос** — одна строка в `api/endpoints.ts` и, если он читается через
кеш, одна фабрика в `api/queries.ts`. Настройку соединения копировать не нужно.

## Разбор участка обработки данных

### Пересчёт корзины — `features/cart/model.ts`

**Частота вызова.** Самое частое действие на этих экранах: каждый клик по «+» / «−» и
каждый символ в поле количества. На одно изменение функция вызывается один раз сразу
(оптимистичное обновление) и ещё раз при откате, если сервер отказал. Результат
перерисовывает карточки каталога и строки корзины.

**Число проходов.** Один. `collect()` за единственный обход строит новый массив позиций и
тут же накапливает `quantity` и `subtotal`, а признак «позиция уже была в корзине»
выставляется в том же проходе. Прямолинейный вариант — `map()` для замены, `filter()` для
удаления, `some()` для проверки наличия и два `reduce()` для итогов — дал бы пять обходов и
два промежуточных массива при том же результате.

**Выделение памяти.** Один новый массив и ровно один новый объект — для изменившейся
позиции. Остальные позиции возвращаются по прежней ссылке, поэтому React перерисовывает
одну строку, а не весь список. Аккумулятор наполняется `push`, а не пересоздаётся через
`[...acc, item]` — иначе на N позициях получилось бы N промежуточных массивов и
квадратичная стоимость.

### Сопоставление каталога с корзиной — `lib/collections.ts`

Каталогу нужно для каждого товара знать, есть ли он в корзине. `find()` внутри карточки
дал бы N×M сравнений на каждый рендер (N товаров × M позиций). Вместо этого один `Map`,
построенный за один проход и пересобираемый только при изменении корзины (`useMemo`), —
дальше N обращений по O(1). Тот же `indexBy` используется для остатков на странице корзины.

## Как устроено

```text
apps/web/src/
  api/
    http/              ядро работы с сетью, ничего не знает про домен
      client.ts        сборка клиента из четырёх частей
      transport.ts     отправка: fetch, таймаут, повтор потерянных запросов
      parse.ts         чтение тела, конверт, разбор ошибки
      messages.ts      перевод ошибки в понятный вид
      error-texts.ts   словари: код API в текст, ошибка поля в подсказку
      errors.ts        класс AppError и предикаты
      idempotency.ts   слоты ключей Idempotency-Key
      types.ts         типы транспорта, клиента и ошибок
      constants.ts     статусы для повтора, таймауты, задержки
      utils.ts         сборка URL, признак идемпотентности, пауза
    client.ts          единственный настроенный экземпляр клиента приложения
    session.ts         гостевая сессия: токен, единственное создание, сброс
    endpoints.ts       все запросы — по одной строке на запрос
    queries.ts         ключи кеша и настройки чтения
    types.ts           типы API из @checkout/contracts, своих копий нет
    constants.ts       адрес API, ключи хранилища, интервалы и сроки жизни
    utils.ts           unwrap и предикаты статусов оплаты
  ui/                  примитивы; types.ts и constants.ts — рядом
  features/            экраны: catalog, cart, checkout, order, shell
  lib/                 форма, хранилище, формат, индексы + types/constants
```

В каждой папке действует одно правило: компоненты и функции лежат в своих файлах, а типы,
константы и чистые утилиты — в соседних `types.ts`, `constants.ts`, `utils.ts`. Магических
чисел и строк в разметке нет.

## Принятые решения

**Гостевая сессия.** Токен подставляется провайдером заголовков лениво: первый же
защищённый запрос создаёт сессию, параллельные запросы ждут один промис. Отдельного
«шлюза ожидания сессии» перед рендером нет. `401` перехватывается один раз: токен
сбрасывается, запрос повторяется с новым.

**Идемпотентность.** Ключ привязан к отпечатку тела операции (`api/http/idempotency.ts`):

- то же тело → тот же ключ → повтор вернёт уже созданный объект (`200`), а не второй заказ;
- изменившееся тело (например, новый `quoteId` после пересчёта) → новый ключ автоматически;
- явный `rotate()` — когда пользователь начинает новую попытку оплаты после отказа или отмены.

Слоты лежат в `localStorage`, поэтому перезагрузка страницы не создаёт второй заказ.

**Повтор потерянных запросов.** Транспорт сам повторяет сетевые сбои и `5xx` — но только
для безопасных методов и для `POST` с `Idempotency-Key`. Поэтому повторы React Query
отключены: дублировать их незачем.

**Расчёт доставки.** `POST /api/quotes` вызывается внутри `useQuery` с ключом
`[cartVersion, delivery]`: расчёт однозначно определяется этой парой, поэтому кешируется
как обычное чтение и не плодит лишних расчётов. Адрес курьера проходит через debounce
350 мс. `409 CART_VERSION_CONFLICT` перечитывает корзину — вместе с версией меняется ключ,
и расчёт уходит заново без действий пользователя.

**Устаревшая корзина и расчёт.** Перед созданием заказа корзина перечитывается всегда: она
могла измениться в другой вкладке. Если итог отличается от того, что человек видит на
экране, заказ не создаётся — показываем новую сумму и просим нажать ещё раз. Если корзина
изменилась уже после расчёта и сервер ответил `QUOTE_EXPIRED` или `CART_VERSION_CONFLICT`,
расчёт делается заново по тому же правилу.

**Оплата.** Успех определяется статусом заказа на сервере (`paid` + `succeeded`), а не
ответом на запуск оплаты. Текущая попытка восстанавливается из `GET /orders/{id}/payments`,
поэтому перезагрузка страницы во время оплаты продолжает отслеживание. Опрос статуса живёт
в `refetchInterval` и останавливается сам на конечном статусе и при уходе со страницы.

**Устаревшие ответы.** Каждое чтение идёт со своим `AbortSignal`; React Query применяет
только последний ответ на ключ. Ответ на запись никогда не подменяет более свежие данные:
после мутаций данные перечитываются, а не собираются на клиенте.

**Форматирование.** Суммы, склонения и даты собираются вручную в `lib/format.ts`, без
`Intl`: это несколько строк понятного кода, поведение не зависит от набора локалей в среде
и полностью покрыто тестами.

**Доступность и адаптив.** У полей есть подписи, ошибки связаны через `aria-describedby`,
первое поле с ошибкой получает фокус. Кнопка оформления намеренно не блокируется на
незаполненной форме: заблокированная кнопка не объясняет, чего не хватает. Кольцо фокуса
сделано на `outline` — оно повторяет скругление элемента и не обрезается родителями с
`overflow: hidden`. Модальное окно — нативный `<dialog>`: ловушка фокуса, Esc и возврат
фокуса работают без единого слушателя. Проверены ширины 1280 и 390 пикселей.

## Проверенные сценарии

Основной путь и устойчивость проверены вручную и прогоном в браузере (Playwright,
скрипты в проект не входят):

- каталог грузится из API, товар с нулевым остатком не добавляется;
- количество меняется, позиция удаляется, состав и итог совпадают с `GET /api/cart`;
- превышение остатка: сервер отклоняет запрос, корзина откатывается к прежнему состоянию;
- оба способа доставки со своими полями; смена доставки и состава корзины даёт новый
  расчёт, стоимость доставки и итог берутся из ответа сервера (в том числе бесплатная
  доставка от 5 000 ₽);
- оплата картой: успех, отказ банка, отмена, повтор после каждого из них;
- наличные: заказ сразу подтверждён (`confirmed` / `unpaid`), ни одной попытки
  онлайн-оплаты не создаётся;
- потерянный ответ на `POST /api/orders` не создаёт второй заказ;
- двойное нажатие «Оформить» и «Оплатить картой» создаёт один заказ и одну попытку;
- перезагрузка восстанавливает сессию и корзину; перезагрузка во время обработки оплаты
  доводит заказ до статуса «оплачен»;
- сбой сети не стирает форму, повтор доводит оформление до конца;
- корзина, изменённая в другой вкладке: показываем новую сумму и просим подтвердить,
  после подтверждения заказ уходит с актуальным составом и итогом;
- то же при гонке — когда корзина меняется уже во время создания заказа;
- опрос статуса прекращается после ухода со страницы;
- пустую корзину оформить нельзя;
- форма проходится с клавиатуры: Tab по полям, стрелки в радиогруппах, Enter отправляет;
- при незаполненных полях фокус уходит на первое проблемное, ошибка связана с полем через
  `aria-describedby`;
- ширина 390 пикселей: сценарий проходится целиком.

Юнит-тестами закрыта чистая логика: пересчёт корзины, построение индекса, правила ключей
идемпотентности, политика повторов транспорта, перевод ошибок API в текст и в ошибки полей
формы, форматирование сумм и склонений (`npm run test:web`).

## Известные недоработки

- Автотестов интерфейса в репозитории нет: браузерные сценарии прогонялись отдельно, в
  проект вынесены только юнит-тесты чистой логики.
- Нет виртуализации списков — на учебном каталоге из четырёх товаров она не нужна.
- Пункт выдачи выбирается списком радиокнопок, без карты и поиска.
- Тёмная тема следует системной настройке, переключателя в интерфейсе нет.
- История заказов отдельным экраном не сделана: незавершённый заказ показывается баннером
  на каталоге и в корзине, остальное — по прямой ссылке.
